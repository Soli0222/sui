# 概要

残高予測は、将来の入出金を一つずつ並べて残高を積み上げた結果である。
その一つひとつが**予測イベント**で、生成元は三つに限られる。

- 固定収支：給与、家賃、口座間の定期振替。
- クレジットカード請求：カードごとの引き落とし。
- ローン返済：口座引き落としのローン。

サブスクはこの中にない。
理由は [サブスク台帳](./subscription-ledger.md) にある。

予測イベントはデータベースに保存しない。
リクエストのたびに、その時点の登録内容と実取引から組み立て直す。
固定収支の金額を直すと、過去分も含めて予測が一斉に変わるのはこのためである。

# イベント ID

イベントは決定的な ID を持つ。

| 生成元 | ID の形 | 例 |
|--------|---------|-----|
| 固定収支（月次） | `recurring:<id>:<YYYY-MM>` | `recurring:8f3a...:2026-08` |
| 固定収支（週次） | `recurring:<id>:<YYYY-MM-DD>` | `recurring:8f3a...:2026-08-14` |
| カード請求 | `credit-card:<id>:<YYYY-MM>` | `credit-card:1c92...:2026-08` |
| ローン返済 | `loan:<id>:<YYYY-MM>` | `loan:4e07...:2026-08` |

同じ ID が二度生成されても、先に登録されたほうだけを採用する。
確定済みの取引は `forecastEventId` にこの ID を持ち、同じ ID の予測イベントは一覧から取り除かれる。
`forecastEventId` には一意制約があるため、同じイベントを二重に確定することはできない。

# 生成の範囲と日付シフト

表示範囲は当月から `forecastMonths - 1` か月後までである。
ただし固定収支の候補は、その前後 1 か月ぶんまで広げて生成する。
月初や月末の予定が営業日シフトで隣の月に動くことがあり、範囲の端で取りこぼすためである。
生成したイベントは、基準月かシフト後の日付のどちらかが表示範囲に入っていれば採用する。

シフトの規則は [スケジュールと営業日シフト](./schedule-and-business-day.md) を参照。

# 並び順

同日のイベントは次の順で並べる。

1. 日付の昇順。
2. 種別（`income` → `transfer` → `expense`）。
3. 生成元の優先度（固定収支 10、カード請求 20、ローン 30）。
4. 登録時の `sortOrder`。
5. 説明文の辞書順。

収入を支出より先に置いているのは、同日に給与と引き落としがある月に、途中経過だけがマイナスに沈むのを避けるためである。

# 期日超過と確定

予定日を過ぎたイベントは自動では確定しない。
予定額と実際の引き落とし額が一致するとは限らないからである。
未確定のまま日付だけ過ぎたイベントは `overdueForecast` に入り、確定を促す。

確定は `POST /api/dashboard/confirm` で行う。
リクエストには対象のイベント ID と、実際の金額、対象口座を渡す。
処理は口座残高の更新と取引の作成を同一トランザクションで行い、`forecastEventId` に元のイベント ID を記録する。

- 振替イベントは、出金元と入金先の少なくとも一方が必要で、両方が同じ口座であってはならない。
- 出金元と入金先の通貨が違う振替は受け付けない。
- 既に確定済みの ID を指定すると 409 を返す。

確定を人間の操作に残しているのは、金額の突合を機械に任せないという設計判断である。
UI からでも MCP 経由でも、確認したうえで叩く点は変わらない。
