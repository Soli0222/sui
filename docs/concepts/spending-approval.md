# 独立台帳にする理由

支出決裁は、買い物の前に「いま買ってよいか」を審査するための機能である。
カード引き落としの成立だけを判定するものではない。
通常決裁・購入記録は口座残高、取引、カード請求、カード仮定額を更新しない。
通常予算とカード仮定額は同じ支出の別の見方であり、合算しない。[^specification]

補正予算は、利用を許可した既存口座から購入費用を振り替えるための予算である。
口座の保護額には既存の `balanceOffset` を使う。
移行時の `supplementalBudgetEnabled` は全口座で false である。
補正予算の承認のみが既存の `RecurringItem` に単発 transfer を作成する。
新しい予測イベント生成元は追加しない。

# 設定と状態

決裁対象金額は入力値以上を対象とするが、未満でも任意申請できる。
利用者が合意した初期値は、閾値10,000円・鮮度7日・承認有効14日・資金確認30日である。
新規台帳に設定し、旧台帳の未設定項目も一度だけ補う。入力済みの値とAI設定は保持する。
移行済みであることを`ruleDefaultsApplied`で保持し、その後に設定を空にした場合は設定案内・保留とする。[^simple-application]
通常予算はMFに設定した月額予算をsuiへ登録するものである。
カテゴリ別月額を予算案にまとめ、開始月と終了月（未指定なら継続）を持つ。
変更開始月で旧期間を分け、適用期間の重複を拒否する。
改定前の案と審査スナップショットは保持する。
旧月別予算は登録済みの月だけの期間へ移行し、将来へ延長しない。[^usability-revision]

AI設定はOpenAI・Anthropic・その他から選び、公式サービスの接続先・通信方式はプリセットを使う。
モデル一覧を公式SDKで取得し、一覧取得非対応の接続先ではモデルIDを手入力できる。
接続確認は架空の内容で審査用JSONを検証する。
APIキーはUIで登録・変更・削除する。
秘密値は `SpendingAiCredential` にAES-256-GCMで暗号化し、接続先URLにも結び付ける。
暗号化鍵はDBの外で管理する。
公開API応答、審査スナップショット、監査ログ、エクスポートにはキー本体・暗号文を含めない。
replace復元時は保存キーを消去し、UIで再登録する。
旧環境変数方式は引き続き読めるが、通常画面で環境変数名を入力させない。

# 申請と購入記録

基本項目は買うもの・金額・MFカテゴリ・購入理由・支払手段・購入予定日・使う予算である。
購入予定日は今日、使う予算は通常予算を初期値にする。
一申請は一金額とし、予算対象月は購入予定日の月から求める。
内訳や将来予測の充当元・金額は入力しない。
中項目は任意の入力項目とし、MF明細と利用枠の設定から候補を表示する。
中項目を限定した利用枠が対象大項目にある場合、補正申請の中項目が空欄では承認しない。
緊急性・代替案・関連申請・外貨は補足情報のダイアログに置く。
補正予算の場合は資金元・振替先・日付を指定し、振替額は購入全額とする。[^mf-only]

未完了の申請を一申請一枚のカードとして一覧に並べる。購入完了した申請はローン・サブスクと共通の`ArchivedSection`を使う「購入完了」の折りたたみに移し、履歴と訂正操作を保持する。
取消済みの申請は、購入記録の有無にかかわらず「取消済み」の折りたたみに分類する。取消成功後は操作ダイアログを閉じて成功を通知し、失敗時は入力とエラーを残す。
取消済みカードには取消日時・理由を表示し、審査結果は取消前の結果と明示する。購入記録と履歴は保持し、購入記録がある場合は併記する。
1行目に申請名・購入予定日・予算区分・金額・状態、2行目に審査・購入・変更・根拠・履歴・その他操作のボタンを配置する。
結果はカード内に表示する。購入入力・購入記録の訂正・根拠・履歴・その他操作はそれぞれダイアログで開く。狭い画面では操作行を折り返す。
「AI審査」と「購入した」はどちらも青い主ボタンとして表示する。承認状態で強調色を切り替えず、未審査・保留でも購入記録を開ける。
通信中は二重操作を防ぐためボタンを無効にする。購入記録を保存しても審査結果を承認へ変更しない。
主な操作は購入記録、AI審査、申請変更とし、根拠・履歴・その他操作はボタンからダイアログを開く。
折り畳みメニューを多用しない。
条件付きは未承認で、条件を反映した再審査が必要である。
通常の承認可はコードの制約検証後に承認し、通常予算には予約を作らない。
例外承認は理由を必須とし、AI審査と分けて残す。
資金不足、予算超過、無効口座、通貨不整合、根拠不足を例外承認で回避しない。

「購入した」で購入日・実額・メモを記録すると、申請の表示状態は完了になる。
MFとの手動・自動照合は行わず、明細待ちを新しく作らない。
未承認の購入も事実として記録でき、購入実額が申請額を超えれば追加審査を案内する。
実額訂正では前の記録を履歴に残す。
購入後の取消や期限切れ、MF取込の変更・削除で購入記録を消さない。
補正予算の承認・取消状態は購入完了とは独立して保持する。

# 通常予算の計算

本節は初版のA+R+F+Q、予算予約、明細配賦による通常支出控除を置き換える。[^mf-only]

```
予算実績 = 取り込んだMFの対象支出
予算残額 = 適用中の月額予算 − MF実績
```

利用日とMF大項目で月・カテゴリを集計する。
振替・集計対象外・収入カテゴリは除き、支出カテゴリの正額は返金として実績を減らす。
補正予算で買った支出もMFに載れば通常のMF実績に含める。
申請の承認・購入・取消、旧配賦や分類によってMF実績を変更しない。
未設定カテゴリも実績を表示し、予算と残額は未設定として示す。

AI審査時だけ、未購入の通常申請について `MF実績 + 今回の購入額` の試算を保存する。
予算50,000円、MF実績20,000円なら予算画面の残額は30,000円である。
12,000円の申請を審査すると試算残額は18,000円だが、予算画面は30,000円のままである。
他の申請額や将来の支出予測は足さない。
購入記録済みの再審査は追加額を0にし、MF反映済みであるとは断定しない。
補正予算申請は口座の資金余力で評価し、通常購入の追加試算額は0とする。
通常予算の登録・超過、直前3か月のMF履歴、当月MFの鮮度は通常申請の承認条件である。
補正申請では参考情報であり、通常予算未登録・超過、MF不足・未取込・更新目安未設定・古いデータだけでは保留せず、登録も要求しない。
未取込月・未完了月の集計0は支出ゼロの証拠ではなく、参考情報の限界として扱う。
補正申請にも資金余力・振替条件、共通の必須設定、購入実額・振替の整合性、購入目的等のAI審査を適用する。
資金余力だけで無条件に承認せず、AIの保留・否認は維持する。
結果は審査時の申請種別で表示し、補正申請では保存された資金元通貨の資金余力と今回振替額を主に示す。
通常予算・MF履歴は根拠画面で参考情報と明示する。
過去の審査は書き換えず、既存の保留申請は再審査で新しい条件を適用する。[^supplemental-policy]

参考履歴は対象月の直前3か月であり、9月なら6・7・8月である。
MF月額実績、確認できる月の中央値・平均・最大を示す。
単発支出も履歴に含め、反復予測への変換や固定費の手動調整は行わない。
申請・購入履歴は別の参考資料として渡し、MFとの重複や未反映を断定しない。
通常申請の通常予算・MFの根拠不足は保留し、使いすぎを理由に登録予算を自動増額しない。

# 共通の審査根拠と追加質問

通常・補正とも、審査日から直近12か月（同日まで、月末は切り詰め）のMFを共通の根拠にする。
購入予定月直前3か月の通常予算計算は従来どおり保持し、この共通根拠とは分ける。
大項目・中項目ごとの月別実績は省略前の全対象支出からコードで集計する。
未取込範囲、月途中、期間初月の一部集計は支出ゼロの証拠にしない。

個別明細には大項目・中項目・内容・メモ・金額・集計対象・振替フラグを渡す。
今回の中項目、対象大項目、特別な支出を優先し、同順位は利用日の新しい順・ID順で最大500件を渡す。
明細の省略件数と、別資料である関連申請の省略件数を記録する。
関連申請は明示的な関連、同じカテゴリ、新しい作成日時の順で最大100件とし、MFに合算しない。
保存するdetailIdsは実際に送った個別明細のIDである。

AIは支出集中・同じ目的の頻度、購入目的と期限性、費用内訳と減額・代替案、総合判断を構造化して返す。
期限があることだけで全額を正当化しない。
別の旅行を二重購入とは扱わず、累積負担として評価する。
参照IDは実在する送信根拠に限定し、対象カテゴリのMF集計がある場合は少なくとも一つ参照を必須とする。
出力形式や参照検証は、AIの判断内容そのものが正しいことまでは保証しない。

AIの追加質問はquestionに一つ持ち、質問または不足情報がある承認可は不正出力として保留する。
設定不足・資金不足等のシステム制約と、利用者が文章で回答する質問を分ける。
申請カードの「回答する」からダイアログを開き、回答保存後に新しい版で再審査する。
回答は先に永続化するため、AI通信失敗後も再入力せず再審査できる。
同じ質問への二重回答、変更前・取消済み・審査中の申請への回答は409で拒否する。
質問・回答・入力条件の指紋・日時を履歴に残し、再審査で参照する。
申請変更後の回答も保持するが、現在の条件に対する回答かを区別する。
回答文で金額・日付等を自動変更しない。条件変更は申請編集で行う。[^review-guardrails]

# 補正予算の繰り返し利用

supplementalLimitsは任意の設定配列であり、既存台帳に利用上限を自動設定しない。
対象は補正全体またはMF大項目（任意で中項目）、期間は直近3か月または12か月、金額はJPY整数、超過時は追加説明または承認停止とする。
0円の設定は対象となる正額申請をすべて超過扱いにする。
複数の枠に該当する場合はすべて適用する。

利用額はMF実績ではなく補正申請単位で数える。
承認した金額・カテゴリ・中項目・最初の承認日をallowanceUseとして保存し、再審査で金額・分類を更新しても件数を増やさない。
旧申請では直近の承認スナップショットを根拠とし、承認履歴がない場合は既存の申請情報を使う。
今回の申請は他申請の集計から除いて一度だけ加える。
購入実額・確定振替額が承認額を超える場合は大きい額を使い、外貨はJPY換算する。

未使用の取消・期限切れ・下書き・保留は枠を解放する。
承認済み未使用の予約は期間外でも含め、購入・振替済みは承認日が期間内なら取消後も含める。
資金返却は利用履歴を消さず、枠を復活させない。
購入済み・振替確定済みの分類や換算率を編集して利用額を移すことはできない。
期間は審査日基準とし、購入予定日を未来にしても枠の判定期間をずらさない。

承認停止の上限超過はコードで保留し、AIや例外承認では回避しない。
追加説明の目安超過はシステムが質問を保存し、現在の入力・ルール・利用額に対応する回答を必要とする。
回答後もAIの審査を通す必要があり、例外承認では代替しない。
利用額・条件が変われば説明を再確認する。
承認直前に他の申請や設定の変更を既存の版検証で検出し、古い根拠では承認しない。
枠の期間・他申請額・今回額・設定額・超過時の扱いを審査スナップショットと根拠画面に残す。[^review-guardrails]

# MF CSVの取り込み

MF公式の列は計算対象、日付、内容、金額（円）、保有金融機関、大項目、中項目、メモ、振替、IDである。[^mf-format]
2026-09-06に利用者提供の2026年8月分ファイルで、CP932、日付形式YYYY/MM/DD、0/1の区分値、明細IDの存在を確認した。
内容はテストデータへ転用していない。
テストはすべて架空の店名・金額・IDから作る。

UTF-8（BOMあり・なし）とShift_JISを自動判定して取り込む。
引用符、引用内改行、カンマ、空欄、列数、日付、int32金額、区分値を検証する。
不正行は行番号付きで表示し、月の差し替え全体を止める。
正常行だけで月全体を置き換えない。
元の各列と決裁用の補足を分けて保持する。
カテゴリはMFを正とし、大項目を予算単位、中項目を明細表示に使用する。
旧カテゴリ別名は対応先が一意な場合にMF大項目へ移し、同じ大項目になる予算額は合計する。
曖昧な旧カテゴリは自動変更せず、MFカテゴリで予算・申請を修正する。
支払元は登録済み口座・カードのIDへ任意に紐づけ、未登録ならMF名のまま利用できる。

ファイルのSHA-256、対象期間、日時、行、エラー、解決結果を取込履歴へ保存する。
対象月は明細日付で判定し、空ファイルはファイル名、最後に対象月の選択で補う。
複数月・未来の利用日を含むCSVは取り込まない。
当月は取込日までの月途中のスナップショット、過去月はその月のCSVとして扱う。
最終明細日を期間の終端とはみなさない。
これはMFに現時点で記載された内容の取り込みであり、カード等から遅れて反映される購入の不存在までは保証しない。
当月の更新目安を超えたデータは再取込を案内する。
明細IDがある場合はそれで同一性を判定する。
IDがない重複候補には既存更新、別購入として追加の選択を求める。
同日・同額・同店というだけで別購入を統合しない。
プレビューで追加・変更・前回だけの明細を示し、利用者の確定で対象月を原子的に差し替える。
前回だけの明細は現在の実績から論理削除するが、元の取込・購入・配賦履歴は保持する。
変更・削除はMF実績だけに反映し、購入完了状態は変えない。
プレビュー以降に台帳が更新された場合は409で再プレビューを求める。
変更前後はプレビューと取込履歴に残す。MF明細画面は原文を確認するビューアーとする。

# 旧データの保持

旧内訳、購入配列、配賦、分類、予定、審査スナップショットを削除せず、エクスポート・復元で保持する。
旧購入記録は合計額を購入実績として表示し、明細への配賦なしで完了とする。
新しい購入記録は`purchaseRecord`に持ち、旧配列を上書きしない。
旧複数内訳申請は履歴を保持し、条件変更は新規申請で行う。
新規入力APIは平坦な`amount`と`category`を受け、保管時は旧形式の一内訳へ変換する。
`plans`と`allocations`は履歴・復元専用で、新しい操作と計算では使用しない。
計算型の`R`・`F`等は旧履歴の復元互換のため残し、新規計算では0または空配列を返す。
旧審査結果は旧方式と表示し、現在の予算残額として見せない。

# 補正予算と既存振替

利用可能額は `現在残高 − balanceOffset − 未確定の資金拘束額` である。
未確定入金は加算しない。
承認済みの未確定振替は期日を問わず拘束に含める。
その他の出金・振替は、設定確認期間末と今回振替日の遅い方までを数え、過期日の未解決出金も含める。
反復予定を無限に差し引かない。
承認の予約と生成した振替予定はイベントIDで一度だけ数える。

承認と単発予定作成は同じSerializableトランザクションで実施する。
単発予定はmonthly、interval=1、startDate=endDate、dayOfMonth=その日、dateShiftPolicy=noneである。
再審査は関連する同じ未確定予定を更新し、古い予定を増やさない。
両口座必須、同一口座不可、削除済み不可、通貨一致を検証する。
未承認・審査中・未購入の期限切れでは振替を確定しない。
予定収支画面から関連予定を再有効化するときにも、現在の承認状態を検証する。
確定処理は決裁台帳の行ロックを取消・再審査・予定編集と共有し、残高更新のトランザクション内で承認状態と予定の有効性を再確認する。
関連予定の更新・確定は台帳の版も進め、古いSerializableスナップショットで始まった取消・再審査を競合として拒否する。
購入済みの承認は期限日後も保持し、旧形式の購入済み・完了状態でも承認実績があるものは引き継ぐ。
実額は予定額と異なっていても記録でき、差分は要確認として保持する。

振替の確定は既存の `POST /api/dashboard/confirm` に任せる。
決裁は `forecastEventId` を持つ実取引から利用済み状態と実額を導出する。
予定だけを見て利用済みにはしない。
実額差・予定の外部変更・外部取消は要確認として表示する。
購入記録が先でも振替予定は残り、振替が先なら資金利用済みでも購入記録は未登録であり得る。

未確定取消は関連する元の振替予定を無効化・論理削除し、拘束を解放して予定収支一覧から除く。
申請の関連ID・取消履歴・購入記録は保持する。
関連表示は履歴のID数ではなく、照会時に導出した振替状態を使う。
口座管理は有効な未確定振替、未解決の承認拘束、確定実額等の差分がある申請を表示し、未使用取消・未使用期限切れ・差分のない振替完了は除く。
予定収支の関連表示も対応が必要な未確定振替に絞り、取引画面では確定取引との関連を履歴として残す。
取消済みでも有効な返却予定は表示する。
未確定予定を取り消した後は、その予定の過去の変更差分を要確認にしない。
資金利用を終えた申請や未使用取消に、現在の口座の利用不可・削除・資金不足を理由とする準備の警告を付けない。
有効な返却予定の口座不足と、確定取引の差分は引き続き確認する。
購入額と資金利用額の差分は、実際に返却済みの額を差し引いて判定する。余剰額を返却して購入実額と一致すれば、その差分の警告は解消する。
取消後に全額を返却済みの場合も、購入記録を保持したまま資金準備の警告を解消する。
既存の取消済み申請に残る無効な未確定振替予定も、DB移行時に論理削除する。
replace復元でも、取消済み申請の元の未確定予定を無効化・論理削除する。確定済み・返却・有効な申請の予定と台帳の履歴は保持する。
編集・再審査・期限切れによる一時的な無効化は論理削除しない。取消後に編集して再承認する場合は、同じ関連予定を復元して重複作成を避ける。
確定後の取消は取引も残高も復元しない。
資金返却には確定振替と逆方向の関連予定を作り、その実際の確定で残高が変わる。
返却可能額は元の確定利用額から、確定した返却の実額と有効な未確定返却予定の額を引く。
削除・無効化した返却予定は上限を消費せず、履歴を保持したまま再登録できる。
返却予定の編集・再有効化と確定時にも、確定利用額を超えないことを同じ台帳ロック内で検証する。
既存APIは予測確定取引の削除を403で拒否するため、この制限を決裁側で迂回しない。
復元等で確定取引の事実が変わった場合は、再照会時に状態を導出し直す。
期限処理はサーバーの1分間隔のタスクで未購入分を解放し、未購入の未確定振替を無効にする。

画面内で口座・予定・取引を変更したら、関連表示も再取得する。取得失敗は関連なしと区別して表示し、再試行できる。
削除済み予定へのリンクは表示しない。予定・取引へのリンク先は対象IDの専用表示を設け、終了済みの折りたたみ・期間フィルタ・ページ番号にかかわらず対象を確認できる。

# 実装構造と並行更新

`SpendingLedger` は個人用の決裁データを一つのJSONB集約として保持し、独立した版番号を持つ。
申請、購入記録、取込、予算改定、審査スナップショットを同じロックで更新できることを優先した設計である。
金額・関連・状態の検証はサービスで行い、クライアントから集約全体の書き換えは受け付けない。
月別予算の改定履歴、取込履歴、審査履歴、申請の変更履歴を集約内に残す。
既存の口座・振替・取引は引き続き正規化した既存テーブルを正とする。

更新には読んだ版番号を必須とし、古い版は409にする。
承認処理は、審査開始時に入力と根拠を固定し、AI待ち中はDBロックを保持しない。
承認直前に集約版と、口座・予定・確定取引のフィンガープリントを再検証する。
変更があれば保留にして古い結果では承認しない。
AI通信は `spending-ai.ts` に分離し、Chat Completions互換には公式 `openai` SDK、Anthropicには公式 `@anthropic-ai/sdk` を使用する。[^openai-sdk][^anthropic-sdk]
各社のリクエスト・応答型とプロトコルへの追従をSDKに任せ、決裁サービスは共通のテキスト結果を受け取る。
事業者の追加時も、予算計算や承認処理から通信処理を分離したまま拡張する。
設定済みの完全なURLはSDKのリクエストパスとして渡し、ゲートウェイのパス・クエリも維持する。
SDKの自動再試行は無効にし、リダイレクトを拒否する。
応答本文は従来どおり100,000文字を上限とする。
SDKのログ出力と、汎用環境変数からの組織・プロジェクト・別認証トークンの暗黙継承を無効にする。
審査結果は構造化出力のスキーマで検証する。
AIの理由は最大2件・各160文字、不足情報と具体策は各最大1件・120文字に制限する。超過した出力は不正出力として保留する。
MF実績と申請を区別し、購入後の試算残額を今回の購入上限と取り違えないよう指示する。
画面は判定・主な理由・コードで計算した試算残額・次の確認を先に表示し、根拠・履歴はボタンで開く。
既存の長い審査履歴は失わず、要約表示だけを制限する。
AI障害、45秒のタイムアウト、不正出力は保留にする。
外部AIにはDB操作・振替確定のツールを渡さず、店名や利用理由等を信頼しないデータとして渡す。

UIとMCPは同じHTTP APIを通る。
認証、read-onlyトークン、Originガード、監査ログは既存ミドルウェアが適用される。
エクスポート・replace復元は台帳を含み、旧形式で台帳がなければ空として復元する。
振替関連が欠ける不正な復元は受け付けない。
