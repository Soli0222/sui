# 独立台帳にする理由

支出決裁は、買い物の前に「いま買ってよいか」を審査するための機能である。
カード引き落としの成立だけを判定するものではない。
通常決裁・購入記録・MF明細配賦は口座残高、取引、カード請求、カード仮定額を更新しない。
通常予算とカード仮定額は同じ支出の別の見方であり、合算しない。[^specification]

補正予算は、利用を許可した既存口座から購入費用を振り替えるための予算である。
口座の保護額には既存の `balanceOffset` を使う。
移行時の `supplementalBudgetEnabled` は全口座で false である。
補正予算の承認のみが既存の `RecurringItem` に単発 transfer を作成する。
新しい予測イベント生成元は追加しない。

# 設定と状態

決裁対象金額は入力値以上を対象とするが、未満でも任意申請できる。
利用者が合意した初期値は、閾値10,000円・鮮度7日・承認有効14日・資金確認30日である。
新規台帳に設定し、旧台帳の未設定項目も一度だけ補う。入力済みの値とAI設定は保持する。
移行済みであることを`ruleDefaultsApplied`で保持し、その後に設定を空にした場合は設定案内・保留とする。[^simple-application]
通常予算はMFに設定した月額予算をsuiへ登録するものである。
カテゴリ別月額を予算案にまとめ、開始月と終了月（未指定なら継続）を持つ。
変更開始月で旧期間を分け、適用期間の重複を拒否する。
改定前の案と審査スナップショットは保持する。
旧月別予算は登録済みの月だけの期間へ移行し、将来へ延長しない。[^usability-revision]

AI設定はOpenAI・Anthropic・その他から選び、公式サービスの接続先・通信方式はプリセットを使う。
モデル一覧を公式SDKで取得し、一覧取得非対応の接続先ではモデルIDを手入力できる。
接続確認は架空の内容で審査用JSONを検証する。
APIキーはUIで登録・変更・削除する。
秘密値は `SpendingAiCredential` にAES-256-GCMで暗号化し、接続先URLにも結び付ける。
暗号化鍵はDBの外で管理する。
公開API応答、審査スナップショット、監査ログ、エクスポートにはキー本体・暗号文を含めない。
replace復元時は保存キーを消去し、UIで再登録する。
旧環境変数方式は引き続き読めるが、通常画面で環境変数名を入力させない。

申請画面の基本項目は買うもの・金額・MFカテゴリ・購入理由・支払手段とする。
購入日は今日、予算対象月は購入日の月、予算区分は通常予算から始める。
日付・対象月・内訳・緊急性・代替案・関連申請・外貨は詳細にまとめる。補正予算の振替額は購入全額から求める。
新しい買い物は追加分として計算する。登録済みの予定を明示的に選んだ場合だけ、保存時のトランザクションで残存予測額まで重複を調整する。
`request.resolveForecast: true`では、同じ予定に対する内訳の合計や他申請の予約を考慮して`forecastAmount`を決める。
再審査時の競合チェックは維持し、予測の対応をAIだけで推定しない。既存APIの明示額による操作も引き続き検証する。

申請は下書き、審査中、条件付き、保留、否認、承認済み、購入済み・明細待ち、完了、取消、期限切れを区別する。
条件付きは未承認で、条件を反映した再申請・再審査が必要である。
通常の承認可はコードの制約検証後に承認される。
例外承認は理由を必須とし、AI審査履歴と区別して残す。
資金不足、予算超過、無効口座、通貨不整合、配賦上限、根拠不足を例外承認で回避しない。

購入の事実は未承認でも事後申請として残す。
購入額と未購入残額を分け、取消・期限切れは購入の事実を消さない。
増額は申請の改定または関連申請で再審査する。
内訳は品名、額、カテゴリ、対象月、予測充当元・額を持つ。
予算区分は申請ごとに一つである。

# 通常予算の計算

カテゴリ・対象月ごとに `A + R + F + Q` を決定的に計算する。

| 記号 | 意味 |
| --- | --- |
| A | 取込済みの通常支出。振替、対象外、補正予算の配賦分を除く |
| R | 他の承認・購入済み申請のうち、明細に未反映の額 |
| F | 今後の通常支出。購入と重なる充当分を控除する |
| Q | 今回申請の追加分。自分の既存予約をRに重ねない |

予算50,000、A=20,000、R=5,000、F=15,000、Q=12,000なら、月末見込み52,000、残余−2,000となる。
申請前後をともに審査履歴へ保存する。

過去の参照は対象月の直前3か月であり、9月なら6・7・8月である。
期間を確認した月の変動支出の中央値を基準とし、平均、最大、月別実績も表示する。
確認できた当月日数で消費ペースを計算し、過去基準より高ければ高い方を用いる。
未確認日を分母に足さない。
固定予定は月ごとの金額と変更・終了を明示し、過去の変動費基準と区別する。
単発支出を反復予測から除く場合は、利用者の分類理由を保持する。
単発であっても実績と購入履歴には残す。

予測内の買い物には充当元IDと額を指定する。
予定または一般変動費の控除上限を審査資料に表示し、他申請が使った部分を再利用できないようにする。
不明な購入は追加分として扱う。
過去の使いすぎによって登録予算を自動増額しない。

# MF CSVの取り込み

MF公式の列は計算対象、日付、内容、金額（円）、保有金融機関、大項目、中項目、メモ、振替、IDである。[^mf-format]
2026-09-06に利用者提供の2026年8月分ファイルで、CP932、日付形式YYYY/MM/DD、0/1の区分値、明細IDの存在を確認した。
内容はテストデータへ転用していない。
テストはすべて架空の店名・金額・IDから作る。

UTF-8（BOMあり・なし）とShift_JISを自動判定して取り込む。
引用符、引用内改行、カンマ、空欄、列数、日付、int32金額、区分値を検証する。
不正行は行番号付きで表示し、月の差し替え全体を止める。
正常行だけで月全体を置き換えない。
元の各列と決裁用の補足を分けて保持する。
カテゴリはMFを正とし、大項目を予算単位、中項目を明細表示に使用する。
旧カテゴリ別名は対応先が一意な場合にMF大項目へ移し、同じ大項目になる予算額は合計する。
曖昧な旧カテゴリは自動変更せず、MFカテゴリで予算・申請を修正する。
支払元は登録済み口座・カードのIDへ任意に紐づけ、未登録ならMF名のまま利用できる。

ファイルのSHA-256、対象期間、日時、行、エラー、解決結果を取込履歴へ保存する。
対象月は明細日付で判定し、空ファイルはファイル名、最後に対象月の選択で補う。
複数月・未来の利用日を含むCSVは取り込まない。
当月は取込日までの月途中のスナップショット、過去月はその月のCSVとして扱う。
最終明細日を期間の終端とはみなさない。
これはMFに現時点で記載された内容の取り込みであり、カード等から遅れて反映される購入の不存在までは保証しない。
当月の更新目安を超えたデータは再取込を案内し、予測ペースの分母は取り込んだ範囲の日数だけを使用する。
明細IDがある場合はそれで同一性を判定する。
IDがない重複候補には既存更新、別購入として追加の選択を求める。
同日・同額・同店というだけで別購入を統合しない。
プレビューで追加・変更・前回だけの明細を示し、利用者の確定で対象月を原子的に差し替える。
前回だけの明細は現在の実績から論理削除するが、元の取込・購入・配賦履歴は保持する。
変更・削除で明細待ちに戻る購入の未反映額は復元し、二重計上しない。
プレビュー以降に台帳が更新された場合は409で再プレビューを求める。
変更前後はプレビューと取込履歴に残し、既存配賦が参照した版が変われば要確認にする。

# 明細配賦と購入完了

一つの購入に複数明細、一つの明細に複数購入の部分配賦を認める。
明細候補を表示し、利用者が確認した配賦だけを確定する。
明細と購入実額の両方の上限をDB更新トランザクション内で検証する。
購入実額全体が現在のMF明細版に配賦され、購入終了を記録した時点で完了する。
カード請求や引き落としは待たない。

配賦の解除は確認状態を戻すが、そのMF明細がAに含まれる限り、反映済みという帰属を保持する。
これにより、確認を外すだけでAとRに同額を再計上しない。
明細削除や集計対象外への変更でAから消えた額はRへ戻す。
利用者が別の購入へ再配賦するときは、解除済み部分の帰属を同じ更新内で移す。
有効な配賦が残る部分は移せず、先に解除が必要である。
補正予算への帰属は通常予算からだけ除き、元明細と全支出には残す。
返金はMF入金明細から元の購入へ関連付ける。
返金だけで資金元口座に資金が戻ったことにはしない。

# 補正予算と既存振替

利用可能額は `現在残高 − balanceOffset − 未確定の資金拘束額` である。
未確定入金は加算しない。
承認済みの未確定振替は期日を問わず拘束に含める。
その他の出金・振替は、設定確認期間末と今回振替日の遅い方までを数え、過期日の未解決出金も含める。
反復予定を無限に差し引かない。
承認の予約と生成した振替予定はイベントIDで一度だけ数える。

承認と単発予定作成は同じSerializableトランザクションで実施する。
単発予定はmonthly、interval=1、startDate=endDate、dayOfMonth=その日、dateShiftPolicy=noneである。
再審査は関連する同じ未確定予定を更新し、古い予定を増やさない。
両口座必須、同一口座不可、削除済み不可、通貨一致を検証する。
未承認・審査中は振替を確定しない。

振替の確定は既存の `POST /api/dashboard/confirm` に任せる。
決裁は `forecastEventId` を持つ実取引から利用済み状態と実額を導出する。
予定だけを見て利用済みにはしない。
実額差・予定の外部変更・外部取消は要確認として表示する。
MF紐づけが先でも振替予定は残り、振替が先でも購入は明細待ちであり得る。

未確定取消は予定を無効にして拘束を解放する。
確定後の取消は取引も残高も復元しない。
資金返却には逆方向の関連予定を作り、その実際の確定で残高が変わる。
既存APIは予測確定取引の削除を403で拒否するため、この制限を決裁側で迂回しない。
復元等で確定取引の事実が変わった場合は、再照会時に状態を導出し直す。
期限処理はサーバーの1分間隔のタスクで未購入分を解放し、未購入の未確定振替を無効にする。

# 実装構造と並行更新

`SpendingLedger` は個人用の決裁データを一つのJSONB集約として保持し、独立した版番号を持つ。
申請、配賦、取込、予算改定、審査スナップショットを同じロックで更新できることを優先した設計である。
金額・関連・状態の検証はサービスで行い、クライアントから集約全体の書き換えは受け付けない。
月別予算の改定履歴、取込履歴、審査履歴、申請の変更履歴を集約内に残す。
既存の口座・振替・取引は引き続き正規化した既存テーブルを正とする。

更新には読んだ版番号を必須とし、古い版は409にする。
承認処理は、審査開始時に入力と根拠を固定し、AI待ち中はDBロックを保持しない。
承認直前に集約版と、口座・予定・確定取引のフィンガープリントを再検証する。
変更があれば保留にして古い結果では承認しない。
AI通信は `spending-ai.ts` に分離し、Chat Completions互換には公式 `openai` SDK、Anthropicには公式 `@anthropic-ai/sdk` を使用する。[^openai-sdk][^anthropic-sdk]
各社のリクエスト・応答型とプロトコルへの追従をSDKに任せ、決裁サービスは共通のテキスト結果を受け取る。
事業者の追加時も、予算計算や承認処理から通信処理を分離したまま拡張する。
設定済みの完全なURLはSDKのリクエストパスとして渡し、ゲートウェイのパス・クエリも維持する。
SDKの自動再試行は無効にし、リダイレクトを拒否する。
応答本文は従来どおり100,000文字を上限とする。
SDKのログ出力と、汎用環境変数からの組織・プロジェクト・別認証トークンの暗黙継承を無効にする。
審査結果は構造化出力のスキーマで検証する。
AIの理由は最大2件・各160文字、不足情報と具体策は各最大1件・120文字に制限する。超過した出力は不正出力として保留する。
予測の調整不足を資金不足と呼ばず、購入後残額を今回の購入上限と取り違えないよう指示する。
画面は判定・主な理由・コードで計算した購入後残額・次の確認を先に表示し、全根拠・計算内訳・履歴は折り畳む。
既存の長い審査履歴は失わず、要約表示だけを制限する。
AI障害、45秒のタイムアウト、不正出力は保留にする。
外部AIにはDB操作・振替確定のツールを渡さず、店名や利用理由等を信頼しないデータとして渡す。

UIとMCPは同じHTTP APIを通る。
認証、read-onlyトークン、Originガード、監査ログは既存ミドルウェアが適用される。
エクスポート・replace復元は台帳を含み、旧形式で台帳がなければ空として復元する。
振替関連が欠ける不正な復元は受け付けない。
