# 概要

飲み代を 12000 円立て替えた。
この時点で口座からは 12000 円出ており、実取引としてもう記録されている。
後日 4000 円が返ってくると、それも入金として記録される。

残高の側から見れば、話はこれで閉じている。
足りないのは、その二つの取引の「あいだ」に何があったかである。
誰がいくら負担するはずで、そのうちいくらが返ってきていないのか。
割り勘機能が扱うのはこの部分で、金額そのものは残高予測には一切入らない。

債権を予測に足すと、既に反映されている支出を二重に数えることになる。
サブスクを予測に入れない理由と同じ構図である（[サブスク台帳](./subscription-ledger.md)）。

# 構造

- **メンバー**（`Person`）：割り勘の相手。論理削除する。
- **割り勘**（`TransactionSplit`）：日付、説明、総額、分割方法を持つ一件の立替。
- **負担**（`SplitShare`）：割り勘 1 件に対する、メンバー 1 人ぶんの負担額。
- **精算**（`Settlement`）：回収の記録。1 人ぶんで、複数の負担に按分して充当する。
- **充当**（`SettlementAllocation`）：精算 1 件が、どの負担にいくら充てられたか。

負担と精算を分けているのは、複数回の立替をまとめて一度に返してもらう場合があるからである。
一度の精算が複数の負担に跨り、一つの負担が複数回に分けて返ってくることもある。

# 分割方法と端数

自分自身は `SplitShare` を持たない。
自分の負担は、総額からメンバーぶんの合計を引いた残りである。

| `method` | メンバーの負担額 |
|----------|------------------|
| `equal` | `floor(総額 / (メンバー数 + 1))` を全員に |
| `ratio` | `floor(総額 × 各自の比率 / 比率の合計)`。自分の比率 `ownRatio` も合計に含める |
| `amount` | 入力された額をそのまま。合計が総額を超えると 400 |

どの方法でも切り捨てなので、端数は必ず自分の取り分に寄る。
1000 円を 3 人で割ると、メンバーは 333 円ずつ、自分は 334 円になる。
立て替えた側が 1 円多く持つほうが、請求のたびに 1 円を巡る調整をするより実用的である。

# 精算の種類と検証

精算には二種類ある。

- `transaction`：実際の入金に紐づける。JPY の振替取引にだけ紐づけられる。一つの振替取引に対して複数回の精算を記録でき、それらの充当額の合計が取引額を超えない。未充当額がある間だけ追加精算の候補となり、全額充当後は候補から消える。日付は取引の日付を使う。
- `offset`：現金でのやり取りや相殺など、取引を伴わない回収。日付を明示的に渡す。

充当は 1 件ごとに次を満たす必要がある。

- 金額が正であること。
- 対象の負担が、指定した人のものであること。
- 既に充当済みの額と合わせて、負担額を超えないこと。
- 同じ精算の中で、同じ負担を二度指定しないこと。

充当が 1 件でも付いた割り勘は、編集も削除もできない（409）。
回収済みの金額の根拠が後から動くのを防ぐためである。
直すには、先に精算を削除する。

# 状態

負担と割り勘には、充当の合計から求まる状態が付く。

- `unsettled`：充当ゼロ。
- `partial`：一部だけ充当済み。
- `settled`：充当の合計が負担額に達している。
