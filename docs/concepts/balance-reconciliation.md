# 概要

記録は必ずずれる。
現金で払った分を入れ忘れる、口座振替の手数料を見落とす、そもそも何に使ったか思い出せない。
月末に通帳を見ると、アプリ上の残高より 3200 円少ない、といったことが起きる。

このとき残高を直接書き換えて辻褄を合わせると、差が生じたという事実そのものが消える。
sui は差分を消さずに `adjustment` 型の取引として残す。
残高は合うようになり、いつどれだけずれたかも後から追える。

# 照合フロー

`POST /api/accounts/:id/reconcile` に実残高を渡す。

1. `diff = actualBalance - account.balance` を計算する。
2. `diff` が 0 でなければ、当日付で `type: adjustment`、`description: "残高照合"`、`amount: diff` の取引を作る。
3. 口座の `balance` を `actualBalance` に更新し、`lastReconciledAt` を現在時刻にする。
4. `diff` が 0 なら取引は作らず、`lastReconciledAt` だけを更新する。

`diff` は符号付きで、int32 の範囲を超える場合は 400 を返す。

口座編集（`PUT /api/accounts/:id`）で `balance` を直接変更したときも、同じように差分が `adjustment` 取引として記録される。
ただし `lastReconciledAt` は更新されない。
実残高を確認した上でのずれの解消なのか、単なる入力の訂正なのかを区別するためである。

# 並行操作

取引の作成・更新・削除、残高照合、口座編集は Serializable トランザクションで処理する。
変更前の取引や残高もその中で読み、競合した場合は処理全体を再試行する。
削除済みかの確認や調整額の計算だけをトランザクションの外へ出してはならない。
再試行は最大7回とし、なお競合が続く場合は409を返す。
これにより、同じ取引の二重巻き戻しと、同じ差額の調整取引の重複を防ぐ。

# 残高履歴が過去を書き換えない理由

`GET /api/transactions/balance-history` は、現在の残高を起点にして取引を逆算し、過去の残高推移を復元する。
終了日より後の取引を巻き戻して起点を求め、そこから範囲内の取引を日付順に戻していく。

`adjustment` 取引も、この巻き戻しの対象である。
照合で 3200 円のずれを記録すると、照合日より前の残高は 3200 円高いままで復元される。
記録上そうだったからである。
照合の結果を過去に遡って反映すると、その時点で見ていた残高と履歴が食い違う。

# 未決の設計課題

口座残高の直接編集は、将来的に塞ぐ方向で検討している。
一方で、使途不明金の調整は現実に必要であり、照合フローだけで足りるかどうかは決まっていない。
`adjustment` 取引を人手で作る経路を残すのか、照合に一本化するのかは未確定である。

# 長期間の残高履歴

履歴APIは同じDBスナップショットから残高と取引を読み、DB側で収支を集計する。
終了日後の全取引を差し戻すため、件数を切り捨てて過去残高を変えてはならない。
期間が2048日以内なら日次、長期間では最大2048区間に分け、それぞれ最後の取引日の正確な期末残高を返す。
`bucketDays` は集計日数で、取引画面にも集計していることを表示する。
区間内の日々の増減を確認するには表示期間を短くする。
JPY換算は従来どおり取引ごとに丸めてから合計する。

チャートの補間は最大4096点、月の目盛りは最大24個とする。
通常期間は日次表示を維持し、長期間は均等な日付とイベント境界を採用する。
移動平均は残高が一定の区間の累積和から計算し、表示期間の全日数を配列に展開しない。
