# 概要

ダッシュボードの応答は、`packages/backend/src/services/forecast-core.ts` の `buildDashboardCore` が一手に組み立てる。
データベースアクセスは呼び出し側が済ませ、この関数は純粋な入力から純粋な出力を返す。
1400 行のテストが単体テストとして書けているのは、この分離のおかげである。

入力は口座、予定収支、カード、請求データ、ローン、確定済み取引、当日、予測月数、オフセット適用フラグの九つ。
出力は合計残高、最小残高、次の収入と支出、期日超過イベント、予測イベント列、口座別予測である。

# 処理順

1. **候補期間を決める**：表示範囲は当月から `forecastMonths - 1` か月後まで。予定収支の候補生成だけ前後 1 か月ぶん広げる。
2. **予定収支を展開する**：候補月ごとに発生日を求め、営業日シフトを適用し、基準月かシフト後の月のどちらかが表示範囲に入るものを採用する。
3. **カード請求を展開する**：表示範囲の各月について実績額と想定額を突き合わせ、採用額が正のときだけイベントを作る。
4. **ローン返済を展開する**：残額と残回数を確定済み取引から逆算し、月ぶんの返済額を割り直す。
5. **並べて確定済みを除く**：日付、種別、生成元優先度、`sortOrder`、説明の順で整列し、`forecastEventId` が一致する取引があるイベントを落とす。
6. **過去と未来に分ける**：当日より前のイベントは `overdueForecast` に、当日以降は `forecast` に入れる。
7. **残高を積み上げる**：全口座の合計から始めて、イベントを順に適用する。同時に口座別の残高も進める。

各イベントは生成時に ID で重複排除される。
同じ ID を二度追加しようとしても、先に入ったほうが残る。

# 二本の残高

積み上げは二系統ある。

- **合計残高**：全口座の合計に対してイベントを適用する。出金元と入金先が両方とも登録済み口座の振替は、合計を動かさない。
- **口座別残高**：イベントの `accountId` に対応する口座だけを動かす。振替は出金元から引いて入金先に足す。口座が未設定のイベントは、合計だけを動かして口座別には現れない。

口座別のほうは、さらにオフセット適用後の残高と実残高を並行して進める。
[警告レベル](../concepts/disposable-balance.md)の判定に両方が要るためである。

# 通貨の扱い

イベントの金額は登録通貨のまま持ち回り、残高に適用する直前に JPY へ換算する。
`amount` は元通貨、`amountJpy` が換算後で、応答には両方が入る。
換算の規則は [複数通貨と JPY 換算](../concepts/multi-currency.md) にある。

# 期日超過の残高

`overdueForecast` の各行にも残高が入っている。
これは現在の合計残高を起点に、過去の未確定イベントを順に適用した仮の値である。
「これらを確定したら残高はこうなるはず」を示すもので、実際の残高ではない。
